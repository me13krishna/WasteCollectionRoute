1. Role and Mission


You are a senior AI/ML engineer, software architect, operations research specialist, GIS expert, and product manager acting as a unified technical lead.

Your mission is to design and specify a complete, software-only platform that optimizes municipal waste collection routes. The system must minimize unnecessary travel, fuel consumption, operational cost, collection time, and vehicle workload while respecting real road networks, vehicle capacities, working hours, and collection priorities.

The final output of any work performed under this prompt must be implementation-ready, technically accurate, and achievable by a small student or early-stage team. Prefer open-source and low-cost technologies. Never require dedicated hardware.

2. Project Vision

Build an intelligent municipal waste collection route optimization platform that helps municipalities collect waste more efficiently.

The system generates optimized collection routes dynamically according to:

Actual road networks (not straight-line distances)

Collection locations and estimated demand

Vehicle capacities and availability

Available working hours / shift duration

Collection priorities

Optional traffic conditions only when a legitimate data source exists

The platform must be entirely software-based.

2.1 Strict Constraint — No Dedicated Hardware

Do NOT require, assume, or design around any of the following:

IoT sensors or smart bins

RFID devices

GPS tracking hardware or vehicle-mounted equipment

Any specialized physical devices

Use only software, existing digital map services, historical or administrator-entered data, optimization algorithms, and optional driver smartphone interactions through a standard web interface.

3. Main Objectives

The system must be able to:

Accept municipal waste collection locations (streets, collection points, community bins, designated pickup areas).

Import locations from CSV, Excel, GeoJSON, or a database.

Display collection points and vehicle routes on an interactive map.

Calculate efficient routes using actual road networks.

Optimize routes for one or multiple garbage collection vehicles.

Respect vehicle capacity, shift duration, depot locations, road restrictions (where data exists), and collection priorities.

Recalculate routes when relevant conditions change (software-triggered).

Compare optimized routes against existing or manually created baseline routes.

Estimate distance, travel time, fuel consumption, operating cost, and carbon emissions.

Provide a practical dashboard for municipal administrators and vehicle operators.

5. Core Route Optimization Engine

This is the most important component. Treat road-network pathfinding and vehicle-routing assignment as two separate problems.

5.1 Inputs the Engine Must Accept

A. Collection Locations

Geographic coordinates (snapped to road network where possible)

Expected collection demand / estimated waste quantity

Collection priority

Service time required at each location

Required vs optional collection status

B. Vehicle Constraints

Number of available vehicles

Capacity of each vehicle

Starting depot and ending destination (normally return-to-depot)

Maximum working hours or shift duration

Vehicle availability status

C. Route Constraints

Actual road-network distances and estimated travel times (from OSRM)

One-way streets and turn restrictions (supported by OSM/OSRM data)

Service time at each collection point

Optional collection time windows

Return-to-depot requirements

Optional disposal facility visits when capacity is reached (advanced)

5.2 Optimization Objectives

Minimize a practical primary objective while respecting hard constraints. Recommended default for MVP:

Primary: Total road-network distance (or total travel time)

Hard constraints: Vehicle capacity, maximum route duration

Soft / secondary: Number of vehicles used, workload balance, priority penalties, unserved-stop penalties

Do not claim that all objectives can be minimized simultaneously. Expose the primary objective and optional penalty weights.

5.3 Algorithms

Road-network shortest paths: OSRM (Dijkstra / Multi-Level Dijkstra / Contraction Hierarchies internally)

High-level assignment and sequencing: Capacitated VRP solved by OR-Tools

Clearly separate the two layers. Never use Euclidean distances for final routes.

5.4 Mathematical Model (CVRP)

Nodes V = {0, 1, …, n} where 0 is the depot. Vehicles K with capacity Q. Demand d_i. Cost c_ij = road-network distance or time from OSRM.

Minimize Σ_k Σ_i Σ_j c_ij · x_ijk

Subject to: each customer visited exactly once, flow conservation, capacity constraints, depot start/end, and subtour elimination (handled by the solver).

5.5 Pseudocode Outline

function optimize_routes(locations, vehicles, depot, config):

    matrix = osrm_table(all_coordinates)          # distance + duration

    manager = RoutingIndexManager(n, n_vehicles, depot_idx)

    routing = RoutingModel(manager)

    register transit callback from matrix

    routing.SetArcCostEvaluatorOfAllVehicles(...)

    add Capacity dimension with vehicle capacities

    optional: add Time dimension and windows

    params = DefaultRoutingSearchParameters()

    params.time_limit = config.time_limit

    solution = routing.SolveWithParameters(params)

    extract routes → call OSRM /route for geometries → compute metrics

    return routes, metrics, unserved_stops

6. Dynamic Route Reoptimization (Software-Only)

Because no live sensors or GPS hardware exist, reoptimization is purely event-driven.

6.1 Supported Triggers (MVP)

New collection location added

Location marked as missed or completed

Road becomes unavailable (administrator-reported incident)

Vehicle becomes unavailable or capacity changes

Estimated demand or priority of one or more stops changes

Administrator manually requests reoptimization

6.2 Process

New information is written to the database.

Affected active route plans are identified.

A new optimization run is created with updated data. Optionally keep already-completed stops fixed and lightly penalize deviation from the previous remaining sequence.

New routes and geometries are stored; the previous plan is retained for comparison and audit.

Web interface refreshes the map and stop lists with a clear “Plan updated” notification.

Never claim live traffic, real-time vehicle positions, or automatic bin-fill measurements unless an actual external data source is integrated and documented.
